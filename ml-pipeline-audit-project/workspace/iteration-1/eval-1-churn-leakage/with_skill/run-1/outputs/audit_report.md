# ML Pipeline Audit

## Summary
Your instinct is right — the 96% accuracy is not trustworthy, and there isn't just one bug, there are several stacked on top of each other. The biggest one is a genuine target-leakage feature (`days_since_cancellation_flag_set`) that is populated right before a customer churns, which alone could explain most of the score. On top of that, every preprocessing step (imputation, scaling, one-hot encoding) is fit on the full dataset *before* the train/test split, and the "hyperparameter tuning" loop picks its winning model by scoring directly on the test set — so the test set has already been used for model selection by the time you compute the final "test accuracy." Finally, the target is ~5% positive and the only metric reported is plain accuracy, which is close to meaningless at that imbalance (a model that always predicts "not churned" would already score ~95%). Fix the leakage and the tuning-on-test-set issue first — the real number is probably much lower than 96%.

## 1. Data Understanding
The pipeline works with tabular customer data (`customers.csv`) with columns including `customer_id`, `tenure_months`, `monthly_charges`, `total_charges`, `zip_code`, `contract_type`, `support_tickets_last_30d`, `days_since_cancellation_flag_set`, and the target `churned`. Per the comment on line 17, the target is imbalanced at roughly 5% positive. The split is a single random `train_test_split` (line 46).

**Findings:**
- **Warning** — `train_test_split(X, y, test_size=0.2)` (line 46) does not pass `stratify=y`. With a ~5% positive rate, a plain random split risks meaningfully different churn rates between train and test, especially if the dataset isn't very large. Add `stratify=y`.
- **Note** — No `random_state` is set on the split (line 46). This isn't a correctness bug, but it means every run produces a different split and a different reported accuracy, which will make it hard to know if a future change actually helped or if you just got a friendlier split.
- **Note** — Row count isn't shown anywhere in the script/comments, so I can't assess whether there's enough data for the number of features being generated (in particular, one-hot encoding ~4,000 zip codes — see Section 3). Worth checking `df.shape` explicitly since it affects several other findings below.

## 2. Data Handling Correctness
Beyond the split, there's a specific engineered/raw feature whose description points directly at target leakage, and there's no visible deduplication step before the split.

**Findings:**
- **Critical — target leakage via `days_since_cancellation_flag_set`** (comment on lines 36–38, used as a feature via line 41). The comment explicitly says this column "is only populated (non-null) once the internal 'pending cancellation' flag has been set on the account, which happens right before a customer actually churns." That means non-null values in this column are, for practical purposes, downstream of the churn decision itself — the model isn't predicting churn, it's reading off a flag that the business already set once it knew the customer was leaving. This is exactly the kind of feature the checklist calls out: "would this value actually be known before I need to make the prediction?" Here, the answer is clearly no for the population you'd actually want to score prospectively. This is very likely the single largest contributor to your 96% accuracy. **Drop this column from `feature_cols`, or replace it with something that's genuinely known before cancellation is decided (e.g. a flag for *whether* the pending-cancellation process has started, if that's meaningfully earlier than churn itself — and even then, treat it with suspicion).**
- **Critical — train/test contamination via preprocessing fit before split.** `SimpleImputer.fit_transform` (line 20-23), `StandardScaler.fit_transform` (line 26-29), and `pd.get_dummies` (line 33) are all applied to the full `df` before `train_test_split` is called on line 46. The imputer and scaler both compute their statistics (means, std devs) using rows that end up in the test set, so the "test" data has already influenced the features the model is trained on. This is the single most common leakage bug the checklist calls out, and it's present here for both imputation and scaling. **Split first, then `fit` the imputer/scaler on `X_train` only and `transform`-only on `X_test` — ideally by wrapping both inside an `sklearn.pipeline.Pipeline`/`ColumnTransformer` so this can't regress.**
- **Note** — No deduplication step is visible before the split. If `customers.csv` could contain duplicate or near-duplicate rows (e.g. re-exports, multiple snapshots of the same customer), those could land on both sides of the split and inflate test performance further. Worth a quick `df.duplicated().sum()` check if you haven't already ruled this out.
- **Note** — No `random_state` set on `LogisticRegression` (line 53) or the split. Doesn't bias results, but hurts reproducibility — flagged again here because it also affects whether your hyperparameter selection (Section 5) is even stable run to run.

## 3. Feature Engineering
Imputation and scaling are handled with `SimpleImputer`/`StandardScaler`, and categoricals go through `pd.get_dummies`. `engagement_score` is a hand-built feature from two existing columns.

**Findings:**
- **Critical (cross-referenced from Section 2)** — Imputer and scaler are `fit` on the full dataframe before the split (lines 19-29), not fit-on-train/transform-only-on-test. See Section 2 for the fix.
- **Warning — high-cardinality one-hot encoding.** The comment on line 32 notes `zip_code` has ~4,000 unique values, and line 33 one-hot encodes it directly via `pd.get_dummies`. This explodes the feature space by thousands of sparse columns, which will hurt a regularized linear model's ability to generalize (many zip-code columns will be near-unique to a handful of customers, effectively acting as weak customer identifiers) and makes the "hyperparameter tuning" search space (Section 5) even less trustworthy. **Use frequency encoding, target encoding (with proper CV to avoid its own leakage — see checklist), or drop to a coarser geography (e.g. first 3 digits of zip) instead of raw one-hot.**
- **Note — `engagement_score` (line 39)** is built from `support_tickets_last_30d` and `tenure_months`, both of which appear to be legitimately pre-outcome features, so this specific engineered feature doesn't look like leakage on its own. Just flagging that it's built from the *scaled* version of `tenure_months` (since scaling already happened on line 27-29) and the *imputed but unscaled* `support_tickets_last_30d` — mixing a standardized and a raw-scale column into one derived feature is unusual and worth double-checking it does what you intend once the fit-before-split issue is fixed and the pipeline is reordered.
- **Warning — no encapsulation.** There is no `Pipeline`/`ColumnTransformer` anywhere in the script; every preprocessing step is a manual `fit_transform` call on the shared `df`. Beyond causing the specific leaks above, this is a structural risk: it makes it very easy to reintroduce leakage later (e.g. adding a new preprocessing step and forgetting to split first), and it means the hyperparameter loop in Section 5 can't refit preprocessing per fold even if you wanted it to. **Wrap the imputer, scaler, and encoder in a single `ColumnTransformer` inside a `Pipeline` with the classifier as the final step.**

## 4. Model Selection & Preprocessing Fit
`LogisticRegression` is used for a binary classification target (`churned`), which is an appropriate model family for this problem.

**Findings:**
- **Note** — Scaling (`StandardScaler`) and one-hot encoding are the right preprocessing choices for logistic regression (a linear, scale-sensitive model) — the model/preprocessing *type* match is fine, only the *timing* (fit before split) is the problem, already covered in Sections 2–3.
- **Warning — no handling of class imbalance.** With ~5% positive rate and plain `LogisticRegression(C=..., max_iter=1000)` (line 53), the model is optimizing for overall accuracy by default, which on this imbalance is trivially satisfied by leaning toward predicting the majority class. There's no `class_weight="balanced"`, no resampling (e.g. SMOTE), and no threshold adjustment. This ties directly into Section 6: even after leakage is fixed, accuracy alone will still look deceptively good unless imbalance is addressed. **Add `class_weight="balanced"` (or resample the training set) and evaluate with imbalance-aware metrics.**

## 5. Hyperparameter Tuning
`GridSearchCV` is imported (line 7) but never actually used. Instead, lines 48-59 manually loop over `C` values, fit a fresh `LogisticRegression` on `X_train`/`y_train` for each, and score each one directly on `X_test`/`y_test`, keeping whichever `C` scores highest on the test set.

**Findings:**
- **Critical — tuning via the test set.** This is exactly the leakage pattern the checklist warns is easy to miss because it "looks like just checking a few options": `model.score(X_test, y_test)` (line 56) is used to select the best `C` among five candidates. Once the test set has been used to pick a hyperparameter, it is no longer a held-out set — the "test accuracy" reported afterward (line 63) reflects a config that was explicitly chosen because it did well on that exact data, not because it generalizes. Combined with the imbalanced target, this makes the final number doubly inflated. **Use `GridSearchCV` (already imported!) with cross-validation on `X_train`/`y_train` only — e.g. `GridSearchCV(LogisticRegression(max_iter=1000), param_grid, scoring="average_precision", cv=5).fit(X_train, y_train)` — and only touch `X_test`/`y_test` once, after the best `C` is chosen from training-data CV.**
- **Note** — The search space (`C: [0.01, 0.1, 1, 10, 100]`) is a reasonable, small grid for a single hyperparameter — grid search is a fine method here once it's pointed at CV on training data instead of the test set.

## 6. Evaluation
The pipeline reports a single number: `accuracy_score(y_test, y_pred)` (line 63), computed on the `X_test`/`y_test` split from line 46 — the same split that was already used to select `C` in Section 5.

**Findings:**
- **Critical — the reported number's provenance is broken.** As covered in Section 5, `y_test` was already used to choose the best model among 5 candidates before this final accuracy is computed. The checklist calls this "the single most important thing to verify" — and here it fails: the test set was not held out through hyperparameter selection, so 0.96 is not a clean estimate of generalization performance.
- **Critical — accuracy is the wrong metric at this imbalance, and no baseline is reported.** With churn at ~5% positive, a model that predicts "not churned" for every customer scores ~95% accuracy while catching zero churners. Your 96% is barely above that trivial baseline, which is almost certainly the real story here rather than the model doing something impressive — especially once the leaked feature (Section 2) is removed, I'd expect accuracy to drop toward that ~95% floor or below unless imbalance-aware training is added. **Report precision/recall/F1/PR-AUC (PR-AUC specifically, since ROC-AUC is also optimistic under heavy imbalance) for the churn class, and explicitly compute and report the majority-class baseline accuracy for comparison.**
- **Warning — no confusion matrix or per-class breakdown.** Only an aggregate accuracy number is printed (line 64). For a rare-event problem like churn, you need to see recall on the churn class specifically (how many actual churners were caught) — an aggregate score can hide that the model is catching almost none of them.
- **Note — single train/test split, no cross-validation.** A single split's accuracy is noisy, more so on a 5%-positive target where the test set may contain relatively few positive examples. Once the leakage/tuning issues are fixed, consider `StratifiedKFold` cross-validation (or at least report a confidence interval) to know how much the number would move on a different split.

## Priority Fixes
1. **Remove `days_since_cancellation_flag_set` as a feature** (or replace it with a genuinely pre-outcome signal) — this is direct target leakage and likely the single biggest driver of the 96% number.
2. **Stop tuning `C` against the test set.** Split, then use `GridSearchCV`/cross-validation on training data only to pick hyperparameters, and touch `X_test`/`y_test` exactly once, at the very end.
3. **Move all preprocessing (imputation, scaling, encoding) into a `Pipeline`/`ColumnTransformer` fit after the split** so it's fit on train only — currently the imputer, scaler, and encoder are all fit on the full dataset before splitting.

After these three fixes, also address the imbalance (`class_weight="balanced"` and precision/recall/PR-AUC instead of accuracy) and the ~4,000-category `zip_code` one-hot encoding — I'd expect the honestly-measured accuracy to be substantially lower than 96%, so don't be surprised or discouraged when it drops; that lower number is the real one.
